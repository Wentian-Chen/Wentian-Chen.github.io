# 常见 Linux 小 bug 的解决方法

在使用 Ubuntu 的过程中，总会遇到一些不大不小的问题：蓝牙模块突然消失、以太网图标不见了、双系统切换后时间错乱、开机总是进错系统。这些问题单看都不复杂，但第一次遇到时往往要搜索大半天才能定位，所以我把踩过的坑整理成了「问题现象 → 原因 → 解决方法」的形式，以后遇到同类问题可以直接对照排查。

先说一下我自己的排查习惯，后面很多步骤都会用到：遇到系统层面的异常，第一件事是看日志——`dmesg` 能查内核报错，`journalctl -xe` 能查服务报错，日志里通常会直接给出线索；第二件事是确认系统的「状态」，比如某个服务是否被禁用、某个配置文件的值是否符合预期；最后才是动手改配置。下面四个问题的排查过程基本都遵循这个套路。

## 1. Ubuntu 掉 AX101 蓝牙

### 问题现象

开机后蓝牙图标消失，蓝牙设备无法被识别。查看内核日志（`dmesg`）可以看到 Intel 蓝牙固件加载失败：

```text
[    2.587972] kernel: Bluetooth: hci0: Failed to load Intel firmware file intel/ibt-1040-1050.sfi (-2)
[    2.589252] kernel: Bluetooth: hci0: Failed to read MSFT supported features (-56)
```

这个现象通常发生在系统更新内核之后：升级前蓝牙还正常，重启后蓝牙就消失了。如果你也遇到了类似的「更新后消失」的规律，大概率就是固件与内核不匹配的问题，可以直接跳到下面的解决方法。

### 原因

`hci0` 是蓝牙控制器的接口，内核在初始化时需要从 `/lib/firmware/intel/` 下加载对应的 Intel 固件文件（`ibt-1040-1050.sfi`）。日志中的 `-2` 表示文件找不到，通常是 `linux-firmware` 固件包与当前内核版本不匹配、固件缺失，或者固件版本过旧导致的。第二条 `Failed to read MSFT supported features (-56)` 是固件加载失败后的连锁反应，只要固件问题解决，这条一般也会跟着消失。

### 解决方法

这类问题与内核和固件版本强相关，我参考了下面的博客思路，更新 `linux-firmware` 固件包、必要时更换内核版本后即可恢复。如果你也遇到类似现象，可以先在终端确认一下 `ls /lib/firmware/intel/` 里是否存在对应的 `.sfi` 文件，再决定是补装固件还是更新内核：

## 2. Ubuntu 没有以太网连接和图标

### 问题现象

进入系统后右上角没有网络图标，以太网无法连接，但 WIFI 开关显示正常。

### 原因

查看网络管理服务（NetworkManager）的状态文件可以发现，`NetworkingEnabled=false`，即网络管理服务认为整个联网功能被禁用了，所以系统层面直接无法上网，这也是图标消失的直接原因。出现这个状态一般是因为系统在关机或休眠时没能正确保存网络状态，属于偶发问题，改回来即可，不必重装系统。

### 解决方法

把 `NetworkingEnabled` 改为 `true` 即可。注意修改配置文件之前要先把服务停掉，改完再启动：

```bash
# 使用下面命令查看ubuntu的网络状态
sudo cat /var/lib/NetworkManager/NetworkManager.state 

# 查询结果如下：
[main] NetworkingEnabled=false WirelessEnabled=true WWANEnabled=true 

# 由于NetworkingEnabled是false状态，所以ubuntu上不了网
# 解决办法就是将其修改true 先关闭服务
service network-manager stop 

# 打开文件
sudo vim /var/lib/NetworkManager/NetworkManager.state
# 修改为NetworkingEnabled=true 

# 再次启动服务
service network-manager start
```

## 3. 修改开机引导项

### 问题现象

双系统开机时默认进入了不想进的系统（比如 Windows 或者某个旧内核版本），希望调整 GRUB 引导菜单中默认选中的选项。

### 原因

GRUB 引导菜单里的每一个选项都有一个序号，第一个选项序号是 0，依次递增。默认选中哪一个，由 `/etc/default/grub` 中的 `GRUB_DEFAULT` 变量决定，把它改成目标选项的序号即可。GRUB 的配置是「修改配置文件 + 重新生成引导表」两步走，只改文件不重新生成是不会生效的。

### 解决方法

```bash
# 开始
sudo vim /etc/default/grub
# 修改 GRUB_DEFAULT=0
# 修改成引导界面，对应的选项。
# 第一行的序号是0，以此类推
# 修改完后保存退出
sudo update-grub
# 结束
```

!!! tip "技巧"
    如果记不清每个选项对应的序号，可以在开机进入 GRUB 菜单时把界面截图或记下来，数清楚目标选项排在第几个，再回来修改 `GRUB_DEFAULT`。修改后必须执行 `sudo update-grub` 重新生成引导配置，否则不生效。

## 4. 双系统时间不同步

### 问题现象

Ubuntu 与 Windows 双系统之间来回切换后，系统时间总是相差 8 个小时左右。

### 原因

Ubuntu 默认把硬件时钟（RTC，即主板上的 CMOS 时钟）当作 UTC 时间处理，而 Windows 默认把 RTC 当作本地时间处理。两个系统对同一块硬件时钟的解释不同，切换系统后显示的时间自然就对不上了。我国在东八区，所以相差正好 8 个小时。这个差异不是硬件坏了，也不是系统坏了，只是两个系统的约定不一样。

### 解决方法

让 Ubuntu 也把 RTC 当作本地时间处理，两边就一致了。在 Ubuntu 的终端执行下面这条命令即可：

```bash
#在Ubuntu的终端执行 即可
timedatectl set-local-rtc 1
```

执行后可以再用 `timedatectl` 确认一下当前状态，同时把两个系统的时间都对好，之后切换系统就不会再出现时间错乱。我个人更喜欢这个方案而不是去改 Windows 的注册表，因为它在 Ubuntu 侧一条命令就能搞定，重装系统后重跑一遍即可。

参考：[ubuntu与windows双系统时间同步问题——简明指南](https://zhuanlan.zhihu.com/p/492885761)

## 附：排查问题的一般思路

把这四个问题放到一起看，其实能总结出一套通用的排查思路，分享给大家：

**第一步，看日志。** 内核层面的问题看 `dmesg`（硬件、固件、驱动相关），服务层面的问题看 `journalctl`（系统服务、应用相关）。日志会直接告诉你「什么失败了、为什么失败」，比盲猜高效得多。本文第一个例子就是靠内核日志定位到固件加载失败的。

**第二步，确认状态。** 很多「假故障」其实是某个开关被关掉了：服务被禁用、配置文件里某个值为 false、启动项被修改。先查状态文件（比如本文第二个例子的 `NetworkManager.state`）和服务状态，再动手改。

**第三步，最小改动。** 一次只改一个地方，改完立即验证。改系统配置前先备份，出了错能快速回滚；不要一次改好几个配置，出问题后根本不知道是哪一步引起的。

**第四步，记录下来。** 把踩过的坑和解决方法写成笔记，下次遇到同样的问题直接翻笔记，能省下大量重复搜索的时间。这也是我写这篇文章的初衷——这些问题我几乎都遇到过不止一次。

## 写在最后

这四个问题都属于「知道了很简单、不知道很头疼」的类型。我的经验是，遇到 Linux 问题先看日志（`dmesg`、`journalctl` 是最高频的工具），再结合系统配置文件去排查，比盲目重装系统高效得多。上面四个问题的解决方法我都在自己的台式机和笔记本上验证过，如果你的发行版本不同，原理一样，命令的包名可能会略有差异。

另外提醒一句：改系统配置文件之前先备份是个好习惯，`.bak` 后缀的备份文件成本极低，但能救回很多「改坏了不知道改了什么」的尴尬时刻。后续我还会继续补充其他踩过的坑，欢迎收藏。如果文中有什么不准确的地方，也欢迎留言指正。
